**Trust anchor и эксплуатационная экономика, 20 ноября 2026 г.**

**Вердикт.** Для эксперимента с положительными наблюдениями подходит Base + PublicNode с OnFinality в резерве, с маркировкой `provider-corroborated` и статусом `unresolved` для неполного окна. При 100–1 000 оплаченных watches в месяц рассмотренные выделенные конфигурации независимой проверки превышают валовую выручку уже по цене хоста. ## A. Собственная derivation и execution verification

**Реалистичная конфигурация.** `base-consensus` (derivation) + `base-reth-node` (L2 execution) из закреплённого релиза `base/base v1.5.6` от 18 ноября 2026 г., с `base-sepolia`, локальным JWT Engine API и отдельными базами клиентов. Релиз `v1.5.0` задаёт минимальную версию для Denim на Sepolia с 21 октября 2026 г. 18:00 UTC. Старый `base/node` архивирован. Для собственной L1 нужны Sepolia EL + Beacon CL после Glamsterdam (6 октября), с EL execution RPC и Beacon API. Актуальные версии-кандидаты из совместимых линеек — Geth `1.17.10` и Lighthouse `8.3.3`. Нужна отдельная проверка blob-serving режима Beacon, например Lighthouse `--semi-supernode` способен реконструировать blobs из колонок, в отличие от предположения о любом дефолтном Beacon. Запуск staking-валидатора для этой задачи не требуется. Для режима derivation оставить `BASE_NODE_SOURCE_L2_RPC` незаданным. Установка этой переменной включает `follow`. Rollup-клиент читает канонические L1 блоки, их транзакции и квитанции, сверяет batch inbox и авторизованного batcher по SystemConfig, восстанавливает calldata/blob frames, deposits и обновления параметров и строит L2 payload attributes по правилам соответствующего форка. Execution-клиент исполняет payload или сопоставляет его с уже проверенным локальным блоком, валидирует переход состояния и commitments. Появление блока из sequencer/P2P влияет на `unsafe`. `safe` следует за успешной derivation из канонических L1-входов, которые ещё могут реорганизоваться. Для `finalized` нужен успешно выведенный L2 блок, для которого финализирован L1 блок, давший необходимые входные данные, включая batch inclusion. Проверка должна учитывать этот L1 блок включения отдельно от L1 origin. Rollup-клиент передаёт L2 finalized hash в Engine forkchoice. Для наблюдателя рабочая проверка — согласованность локального L1 CL и EL, их sync/optimistic статуса, rollup `optimism_syncStatus.finalized_l2`, локального `finalized` и ancestry до нужного блока. Устаревший или застывший head не закрывает окно. **Старт и восстановление.** Исторический replay от доверенной точки старта требует непрерывных L1 входов. Base предупреждает о потребности в архивном источнике blob старше примерно 18 дней. Это протокольный ориентир P2P retention, фактическая глубина REST зависит от Beacon и режима реконструкции. Поддерживаемый resumable snapshot Base Reth V2 ускоряет запуск, но сам по себе не доказывает, что скачанное состояние соответствует каноническому L2. Для независимого результата после snapshot требуется аутентифицированный L2 checkpoint, проверка состояния относительно его root и derivation/execution вперёд до окна из проверенных L1 входов. Холодный replay и восстановление после потери локальной базы требуют либо полного набора исторических входов, либо такой точки восстановления. Раздельно сохранять проверенный прогресс, raw witnesses для повторной проверки, согласованный снимок БД и параметры/хэши checkpoint вне основного диска. После восстановления сверить anchors и догнать backlog до возобновления выдачи проверенных результатов. Измеренных времени bootstrap, RTO, RPO и Sepolia-специфичной скорости replay нет. ### Четыре состояния доказательства

| Состояние | Что устанавливает |
| --- | --- |
| **L1-finalized derivation inputs** | Аутентифицированная Ethereum-финальность сообщения batcher, блоков/транзакций, receipt inputs и blob commitments. На L2 это входные данные. Чтобы получить сами L2 headers, требуется derivation + execution или соответствующее проверенное доказательство их перехода состояния. |
| **L1-posted output claim** | На L1 зафиксирован предложенный `rootClaim` и связанные данные. Даже после финальности транзакции создания game может оставаться `IN_PROGRESS` или закончиться `CHALLENGER_WINS`. Совпавший preimage доказывает привязку к утверждению, а статус утверждения проверяется отдельно. |
| **Resolved и finalized game** | Для принятого root проверять регистрацию DGF, `wasRespectedGameTypeWhenCreated`, retirement/blacklist/pause, разрешение с `DEFENDER_WINS` и срок ASR в аутентифицированном L1 состоянии. Регистрация и численный статус сами по себе недостаточны. При нулевой задержке ASR строгая проверка требует L1 timestamp после `resolvedAt`. Затем нужен финализированный L1 state с действительными условиями. |
| **Independently verified L2 execution** | Собственный A с аутентифицированными L1 входами и стартом или отдельно проверенное доказательство исполнения со связанными L1 inputs, start/end roots, fork config и идентичностью программы. ### Формулы объёма и общий расход

- `N` — число оплаченных watches, `R(N)=0.10N`. Модель на 30 суток с `M=30×86400×5=12 960 000` L2 высотами после Denim. Одно 30-минутное окно содержит 9 000 высот внутри и две граничные, `b=9 002`. У каждого watch свой tuple, окно и результат. Общий ingest и кэш по `chainId/blockHash` повторно используют заголовки, ordered body, receipts и индекс совпадений в общих интервалах. Нельзя переиспользовать допуск отрицательного результата для другого tuple или окна. Среднее число открытых окон `N/1440` равно `0 / 0.069 / 0.694 / 6.944`, без ещё ожидающих finality или очереди. Прибавка для постоянной задержки `L` секунд равна `N×L/(30×86400)`.
- Сценарий **поиска положительных наблюдений** на один источник. Разбить окно на участки по 1 000 блоков и взять 9 запросов логов. Документация Base рекомендует держать диапазоны меньше 2 000, а меньшие лимиты и повторное дробление остаются возможны. Для примера дополнительно на watch 4 чтения заголовков/границ, 2 finalized reads и 1 receipt кандидата. Итого 16 calls и 34 RU до повторов. Размеры ответов, число кандидатов, частота shared polls и дорогих fallback читать из измерений. Chain gate на сессию, дополнительные теги и запросы третьему при сбое учитываются отдельно. При медленном движении finality два чтения тега могут оказаться недостаточны. [Base eth_getLogs](https://docs.base.org/base-chain/api-reference/ethereum-json-rpc-api/eth_getLogs)
- Сценарий **сплошной выборки доказательств**. Наивно `N×b` заголовков. При независимых равномерных началах по циклическому условному месяцу ожидаемое число уникальных высот `H=round(M×(1−(1−b/M)^N))`. Этот сценарий иллюстрирует дедупликацию. Временные всплески меняют и перекрытие, и пиковую скорость работ. При непрерывном ingest `H=M` независимо от `N`. Для checkpoint из B добавить `G` уникальных заголовков от нужных окон до следующих принятых roots, если их уже нет в выборке. При пяти блоках/с даже один час добавляет до 18 000 заголовков. Раздельно считать L1 header/state/receipt proofs, game polling и повторные проверки.
- `p` — доля уникальных проверяемых блоков, Bloom-positive хотя бы для одного активного tuple. `Q=round(pH)` даёт число полных receipt-наборов. Доля неизвестна. Она растёт с совместной нагрузкой и коррелирует с USDC activity. Bloom не проверяет сумму, а совпавшие биты могут относиться к разным логам. Отрицательный Bloom проверяем только у аутентифицированного заголовка. Для положительного Bloom нужны все ordered receipts либо эквивалентное полное локальное исполнение/свидетельство. Полный ordered body надо аутентифицировать по `transactionsRoot` для связывания позиций с tx hashes. Числовой сценарий ниже считает один block read для нужного представления. При отдельном чтении тела добавить до `Q`, а при недоступном batch receipts заменить проблемный batch на до `T_i` запросов за квитанциями всех транзакций блока `i`. `T_i` и хвост размеров неизвестны. [CP2C Bloom, receipt rules and caps](CP2C.md)
- Умножитель попыток `a=1.10` — сценарное допущение, 10% дополнительной работы. `RPC_dense=round(a×(H+Q))`, `RU_dense=round(a×(H+13Q))`. В модели все эти попытки имеют полную стоимость RU, для реальной B/C тарификации отдельно считать успешные ответы, ошибочные ответы и сетевые сбои. Запрос `status` обслуживать из локального durable state. Повтор POST с тем же ключом идемпотентности не порождает второй watch или второй scan. На replay считывать отсутствующие данные по pin/hash с bounded retries. В юнит-экономику входят также статусные чтения, хранение/idempotency, доля повторов оплаты, комиссии, refund и неуспешные работы. Значения не измерены.

### Безубыточность

Полная модель в USD/мес. `C(N)=F + Setup/amortMonths + C_rpc(N) + C_net(N) + C_disk(N) + C_backup(N) + C_recovery(N) + C_ops(N) + N×(f_payment + v_app + expected_refund)`. `F` включает зарезервированные хосты/подписку и выбранное резервирование. Единоразовый setup считают полностью в кассовом первом месяце или амортизируют один раз. Другие члены включают только суммы сверх зафиксированной строки тарифа, без двойного учёта. Операторские часы и RTO/RPO, расходы на сбои, growth storage, банк/settlement и refund остаются неизвестными. Для `v<0.10` и постоянного `v` порог `N_min=ceil(F/(0.10−v))`. ## BLOCKERS

- Ни один live-путь RoundWatch пока не проверяет весь интервал от независимо аутентифицированного finalized anchor до обеих границ watch. Проверенный hash при наличии доверенного якоря связывает header и commitments. Остаются аутентификация самого якоря, envelopes/ancestry и обработка live forks/receipt types.
- Три публичных RPC не дают гарантии общей доступности, сроков выдачи свежего тега и retention. OnFinality не прошёл историческую часть ограниченной пробы. Ни одна из выборок не измеряет production capacity или распределение `p`, размеров полного receipt-набора и повторов.
- Нет измеренных размеров распакованных баз L1/L2, I/O и CPU для cold start, steady state и restore выбранного Sepolia preset. Нет подтверждённой цены доступного исторического blob feed, труда эксплуатации и платного спроса на требуемый класс доказательств.

## FINDINGS

- Положительное провайдерское наблюдение уже воспроизводимо на ограниченных данных. Оно даёт ценность как внешний сигнал для агента при явном уровне доверия и отдельной привязке к инвойсу.
- Каждый 30-минутный watch после Denim включает около 9 000 канонических блоков. Дедупликация полезна при конкурирующих watches, но полное покрытие на 10 000 равномерных watches приближается к непрерывному ingest.
- Сторонний L1 RPC сохраняет решающее доверие к финальности и к части входных данных даже при запуске своего Base узла. L1 output commitments дают отдельный путь к аутентификации hash с другой security model и другой задержкой.

## NOTES

- Возраст provider head, окно наблюдения, время предоставления результата, финальность derivation и состояние withdrawal game — отдельно измеряемые величины. Пока нет основания для SLA или terminal timeout с семантикой «платёж отсутствовал».
- Все исследования выполнены чтением исходников, публичных тарифов и ограниченными запросами. Узлы и подписки не развёртывались. Эксперименты CP1–CP2C и production Algorand остаются вне этой работы. Примерные пороги D зависят от выбранного хостинга, спроса, комиссий и доступности действующей Sepolia.

## Рекомендуемое решение

Выбрать P как минимальный следующий исследовательский путь. Держать Base и PublicNode основными для двухисточникового положительного наблюдения, OnFinality — резервом после ограниченной повторной квалификации с pacing. Положительный факт маркировать `provider-corroborated`. Разрешать `provider-observed` для одного доступного источника только как более слабую метку. При пустом или незавершённом окне сохранять `unresolved` с причиной. Если для продукта необходим доказанный отрицательный ответ за $0.10, решение для текущего предложения — **NO-GO**. Из рассмотренных путей собственная L1 + собственное L2 исполнение даёт наиболее прямое основание для такой гарантии в минутном классе задержки, если её входы и восстановление доказуемы.

## Критерии изменения решения

1. Платящий спрос и согласованный целевой максимум задержки и допустимой доли `unresolved`. Использовать `0.10N−C(N)` по фактическому диапазону спроса, включая месяц с `N=0`, а также peak limits и запас восстановления. При `N≤1 000` для проверенных тарифных строк A нет даже положительного hosted subtotal.
2. Ограниченная квалификация с контрольным известным USDC событием, намеренным пропуском лога, prune/missing receipts, rate limit, stale/regressed finality, failover и replay. Записывать p50/p95/p99 задержки и размера, `p` при параллельных watches, cache hit, повторные попытки, доступную историю и долю незакрытых окон.
3. Для A — воспроизвести независимую L1-финальность, доказуемую стартовую точку L2, совпадение forkchoice, полное окно CP2C и восстановление из snapshot + blobs. Утвердить измеренные resource envelope, цену и время восстановления. Для B — появление регулярно доступных быстрых доказательств с аутентифицированным L1 state и подтверждённым временем от дедлайна до пригодного checkpoint в целевой задержке.
4. Повторно проверить сеть при изменении chain hardfork, версии клиента, DA/retention режима, типа игры, prover/admission политики, существенного сдвига тарифов или официального жизненного цикла Sepolia.
